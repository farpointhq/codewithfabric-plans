Our reported provider cost is running about 83% below what LiteLLM actually bills us. Has anyone upstream hit this with the generic_api callback?
Fabric Large·10:42
▼ web_search Searched the web · 6 results

Short version: the callback reports response_cost from the router’s own price map, not from what the provider actually billed. LiteLLM only fills response_cost when a deployment carries explicit input_cost_per_token / output_cost_per_token; without them it falls back to its bundled table, which still holds the pre-July W&B list prices. Three upstream reports show the same 80–85% gap after a mid-contract reprice.

Two fixes, in order:

  1. Pin explicit per-token costs on every deployment in litellm_config.yaml so the router stops guessing.
  2. Treat response_cost as advisory in the sync job and re-derive from tokens × our own ladder.

Step 2 is the one that survives the next reprice:

10// src/lib/model-pricing.ts
export function providerCostCents(row: UsageRow): number {
  const rate = PROVIDER_RATES[row.model];
  if (!rate) throw new UnknownModelError(row.model);

  return Math.round(
    (row.promptTokens * rate.inputPerMTok +
     row.completionTokens * rate.outputPerMTok) / 10_000,
  );
}

The sync job already carries both token counts, so step 2 needs no schema change — only a backfill over the rows written since the cutover
